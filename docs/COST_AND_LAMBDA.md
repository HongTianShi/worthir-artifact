# 成本与 lambda

WorthIR 使用下式：

```text
utility = effectiveness - lambda * cumulative_cost
```

成本单位和 lambda 都属于任务定义。效用只在该任务及其成本设定内有意义，不能作为
跨数据集分数使用。

必须明确设置 `cost_profile.availability`。`known_at_commitment` 表示路由器可以在
选择路线前使用成本：固定成本公开在 `route_registry.json` 中，逐查询成本公开在
`participant/route_costs.csv` 中。`measured_after_execution` 表示成本只写在评价方
ledger 中，不作为路由器输入。`validate-task` 会检查每个公开成本是否与评分所用
成本相同。

## 选择成本表达方式

应当使用能够回答部署问题的最简单表达方式：

- **预先声明的操作量：** 指定 0、0.25、1.00 等累计相对成本，并说明每个单位
  代表什么。
- **实测延迟：** 在目标环境中重复进行预热后的测量。如果延迟随查询变化，请将
  每个查询的均值写入 `costs.csv`。
- **模型操作量或能耗：** 使用口径一致的实测或计算单位，并计入所有必要的前置阶段。

不要在同一成本设定中混用互不相关的单位。若提供累计成本，每条路线都必须包含
全部前置路线；若提供增量成本，WorthIR 会对传递前置闭包求和，并且每个组件只计
一次。

## 只在有助于解释时归一化

将所有成本除以一个有明确说明的常数，可以提高可读性。例如，如果原始延迟除以
100 毫秒，那么一个成本单位就代表 100 毫秒。改变成本尺度时，lambda 必须按倒数
比例变化，才能保持相同的效用偏好。

## 选择 lambda

Lambda 表示部署方愿意用多少有效性换取一个成本单位。必须在查看评测结果前确定。
其依据可以是服务级别目标、开发集决策或一小组预先声明的偏好。

应报告主要 lambda，并检查若干合理的替代值。如果某个路由结论只在事后选出的
狭窄 lambda 区间内成立，应将其描述为敏感性现象，而不是一般部署结论。

示例值 `0.08` 仅用于演示，并不是新任务的推荐默认值。
